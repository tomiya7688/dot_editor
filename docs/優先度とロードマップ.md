# 優先度区分・実装順・Dot Editor AIとの境界

> 更新日: 2026-11-04 / 状態: 設計案（Issue #69）。
> この文書は実装担当者とIssue管理者に向けたロードマップです。既存Issue #42の2026-10-14時点の作業順を更新し、後日追加されたIssueと将来アプリを区別します。

## 1. 対象と用語

- **Dot Editor本体**: Hyper Dot EditorのRust Core、公開Rust CLI、Python参照実装、軽量GUI、保存互換、配布・CI。
- **Dot Editor AI**: Dot Editorを公開コマンド経由で操作し、テキストから描画プログラムを作る、将来の**独立アプリ**。本体のライブラリにAIモデルや学習フレームワークを組み込まない。
- **P区分**: Issueタイトルの `[P0]` 等で表す、製品と作業の区分。実際の着手順は依存関係・リリース阻害事項から判断する。
- **実装ゲート**: 後続作業を始める前に満たす具体的な受け入れ条件。

## 2. 予約する優先度

| 区分 | 対象 | 意味 | 運用 |
| --- | --- | --- | --- |
| **P0** | Dot Editor本体 | セキュリティ・破壊的障害・出荷阻害・最重要基盤 | 最優先で解消、必要ならリリース停止 |
| **P1** | Dot Editor本体 | 本体の完成に必要な高優先度機能 | 依存を解消して着手 |
| **P2** | Dot Editor本体 | 通常機能・利便性・パフォーマンス | 本体P0/P1を阻害しない範囲 |
| **P3** | Dot Editor本体 | 低優先度の整理・文書・将来検討 | 他の完了条件を確認 |
| **P4** | **Dot Editor AI** | 要件整理・アーキテクチャ・設計漏れの検証 | 本体完成まで設計のみ（#69） |
| **P5** | **Dot Editor AI** | 描画モデル・学習系の実装と実験 | 本体v1とP4設計確定後 |
| **P6** | **Dot Editor AI** | アプリへの統合・ゲームエンジン/自動化との連携 | P5の品質基準通過後 |
| **P7以降** | **Dot Editor AI** | 高度化・拡張・将来構想 | 実測に応じて再計画 |

**重要:** P4以降の数字はAI側の開発段階を兼ねる。P4という表記を「事故の深刻度は低い」と解釈しない。AI側の重大障害は `severity:critical` / `release-blocker` 等の別属性で扱い、必要ならAIのリリースも停止する。本体IssueにP4以降を割り当てず、AI IssueにP0〜P3を割り当てない。

既存の優先度ラベル/タイトルは維持する。評価レビューIssue (#1, #42) は歴史的記録のため一律に実装優先度へ読み替えない。未評価の完了条件があるIssueを形式的にcloseしない。

## 3. 本体の推奨実装順

| 順番 | 優先Issue | ゲート |
| --- | --- | --- |
| 0. 安全性と開発基盤 | #54、#46、配布前に#55 | 信頼ストア/必須CI/出所検証を確認。#55は未署名配布の停止条件と整合 |
| 1. Rustの仕様と中核 | #31、#34、#35、#36、#39 | 非破壊編集、レイヤー、JSON互換、PNGがRust正本で成立 |
| 2. shell操作 | #37、#63 | Rust `pixel-cli` の操作契約、競合編集・revision、安全な保存を検証 |
| 3. E2Eと配布 | #32、#33、#38、#40、#66 | alias/SKILL、実バイナリE2E、3 OSの配布、必須CI、コマンド一覧の自動同梱 |
| 4. 操作性の仕上げ | まず#75（キャンバス入力の登録不具合）。続けて#26〜#30、#67。必要に応じ#64 | GUIキーボード/ヘルプ、通常描画導線。バッチ編集は実測に基づき着手。設計は[キーボード操作](design/keyboard-operation.md) |

## 4. Dot Editor本体v1の完成ゲート

- Rust Coreが任意解像度、保持/破棄、局所分割、レイヤー、JSON保存・読み込み、PNG出力に対応している。
- Rust単体 `pixel-cli` がGUIやPythonなしで起動し、`--help`、機械可読出力、安定した終了コード、主要編集コマンドを提供する。
- Windows x86_64 / Linux x86_64 / macOS arm64で配布物のE2E/検証を実施できる。各成果物の署名・attestationの出荷方針を満たす。
- Python 3.10〜3.14の必要なビルド・互換検査がCIで成功する。RustとPythonのJSON/PNG互換を確認する。
- 競合保存が既存データを上書き消失させず、失敗後に復旧できる。
- コマンド説明表が配布成果物の実際のCLI版と一致している。人間・ゲームエンジン・AIが同一の編集仕様を参照できる。
- 未完成Issueと出荷阻害Issueの受入条件を明示的に確認する。CIが未確認なら完成とは判定しない。

## 5. AIの分離ルールと移行条件

- Dot Editor AIの設計書は暫定的に本リポジトリの [Dot Editor AI設計書](dot-editor-ai/設計書.md) へ保存する。**ここにモデル・学習コードを追加しない**。
- 本体v1完成後、Dot Editor AI用の**別リポジトリ**を作り、設計書とAI固有Issueを移管する。独立したCI、依存管理、実験追跡、ライセンス監査を備える。
- AIはバージョン固定した本体Rust CLIをsubprocess経由で使用する。学習中に内部Rust Coreデータや画像画素を直接書き換えない。
- 本体の改修を要求する場合は、AI固有の命令ではなく**一般利用にも有益な公開コマンド**として本体P0〜P3 Issueへ起票し、通常のCIを通す。
- AIのP4設計が確定しただけではP5実装を解禁しない。本体の正式CLI、必要なバッチ性能、入出力契約の安定性を確認する。

- Issueタイトルは `[P0]`〜`[P7]` のように区分を示し、必要なら `[Dot Editor AI]` を添える。
- Issue本文には、目的、優先度の根拠、依存先、実装済み/設計のみの区別、検証、受け入れ条件を記載する。
- P4設計の親Issueは [#69](https://github.com/tomiya7688/dot_editor/issues/69)。P5/P6/P7の個別実装IssueはAI別リポジトリ開設後に作る。現時点では本体Issueに混在させない。
- 元の構想メモ [提案.md](提案.md) は歴史的構想として残し、AI学習の新しい必須仕様については新設計書を優先する。
