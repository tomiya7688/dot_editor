# Dot Editor AI 設計書 v0.1

> 状態: **将来アプリの設計ドラフト** / 2026-11-04 / 親Issue [#69](https://github.com/tomiya7688/dot_editor/issues/69)
>
> 対象読者: Dot Editor AI の開発者、機械学習担当、評価系担当、Dot Editor CLI担当。
> 優先度: **P4（設計）**。AIの学習・生成実装は本体v1の完成後、**別リポジトリ**で着手する。
> 今回の利用者指定を必須仕様とする。従来の [構想メモ](../提案.md) に含まれる「タグから教師コマンドを作る」「完成画像を解析して描画コマンドを復元する」案は、Actorの学習経路としては採用しない。

## 1. 背景・目的・設計方針

Hyper Dot Editor（以下 **Dot Editor**）は、任意解像度、細部保持/破棄、局所細分化、レイヤー、JSONプロジェクト、PNG出力に対応する。低解像度だけでなく、解像度を十分に増やし追加編集すれば、通常サイズのラスタ画像も制作できる。ただし**解像度を増やすだけでは細部・写真らしさは自動生成されない**。

**Dot Editor AI** は、画像生成のための別アプリ。一般的な画像デコーダや画像を直接出力するモデルを使うのではなく、**文章からDot Editorの編集コマンド列（描画プログラム）を作り、実際に実行してPNGを生成する**。

利用者は「青空の下の赤い家」などの文章を入力し、モデル種別（64×64ドット絵 / 高画質）を選ぶ。アプリはコマンドを実行して作品JSON・描画プログラム・PNGを保存する。入力文が不正、コマンドが失敗、予算に達した場合は失敗理由または最良の途中成果物を返す。利用者の直接操作は入力・実行・結果の確認と保存であり、手動の描画は不要。

## 2. 必須仕様（確定）と提案の区別

| 項目 | 確定した要件 | 設計提案・留保 |
| --- | --- | --- |
| 元の教師データ | **画像と対応するテキストのみ** | command demonstrationや正解軌跡は教師データとして使わない |
| Actorの観測 | **入力テキスト、許されたコマンド仕様、自己のコマンド履歴、成否、数値評価のみ** | 参照/生成画像、画素配列、画像特徴ベクトル、画像から生成した説明文は渡さない |
| 描画方法 | **Dot Editorの編集用コマンドの組み合わせのみ** | Actorが画像ファイルを直接書いたり、任意shell/画像importしたりしない |
| 学習 | **描画→独立評価→再試行を反復し、コマンド操作を学習** | 強化学習/候補探索の方式は比較実験後に選定 |
| モデルの分割 | **64×64ドット絵用と高画質用を別モデルにする** | 共通コードとコマンド文法は利用可能だが、重み・学習データ・報酬・チェックポイントを分離 |
| 本体との関係 | **本体の完成後に別アプリとして開発** | Rust CLIを安定した外部プロセスとして利用 |

ここで「画像を見ない」とは、**生成モデルの入力・コンテキストに画像または画像内容を復元できる視覚情報を入れない**という意味。**外部評価器だけ**は参照画像と生成画像を扱ってよい。評価器から返る数値報酬を用いる学習は、この制約に含まれる「評価を受ける」行為であり、禁止しない。

**非目標**: 画像を直接予測する拡散モデルの利用、画像からコマンドへの逆変換をActorへの教師データにすること、画像特徴量をActorへ埋め込むこと、Dot Editor本体をAI必須にすること。

## 3. 全体アーキテクチャ

```text
学習ペア (caption, target.png)
        │                 target.png (評価器用に隔離)
        ├── caption ────────────────┐
        │                           ▼
        │                    Actor (テキスト専用)
        │                    ├─ 64×64用モデル
        │                    └─ 高画質用モデル
        │                           │ 編集コマンド候補のみ
        │                           ▼
        │                   コマンド検証 / Runner
        │                           │ 正規化argv、制限付き実行
        │                           ▼
        │                     Rust pixel-cli
        │                           │
        │                  作品JSON + 生成PNG
        │                           │ 生成PNGはActorへ返さない
        └── 参照画像 ───────┬────────┘
                            ▼
                  独立した画像評価器
                   (生成PNG, 参照PNG, caption)
                            │
                     有界な数値スコア
                            ▼
                 学習器 / 候補選択・再試行
                            │
                    Actorの重み更新
```

- **Dataset loader**: 画像と文章の対応付け・権利・重複・分割を管理。Actorプロセスにはcaptionのみを配る。
- **Actor**: テキスト条件付きのコマンド方策。画像をロードするAPI、画像埋め込み、画像視覚トークンを持たない。
- **Command validator**: 許されたコマンド名、引数、座標、色、上限、並び順を検証した構造化操作を、shellを介さず`argv`へ変換する。
- **Runner**: Dot Editor Rust CLIを子プロセスで呼び、作品JSONをステージごとに保存・復元。stderr、終了コード、revision、コマンド履歴のみをActorへ渡す。
- **Evaluator**: 生成PNGと学習ペアの画像を独立の権限で読み、参照画像一致度・文章一致度・画質等を計算する。**生成画像も参照画像もActorへ渡さない**。
- **Trainer**: 候補の数値評価、方策更新、モデル検証、探索予算、再現可能な学習ログを管理。
- **Inference service**: 本番では参照画像がない。学習済みActorがテキストから編集コマンドを出し、必要なら生成画像＋入力テキストに対する独立評価だけで再試行する。

## 4. 画像を見ないことの強制

### Actorが受け取れる情報

```json
{
  "prompt": "白い背景に赤いりんご",
  "mode": "pixel64",
  "allowed_commands_version": "version-pinned",
  "stage": "silhouette",
  "stage_budget": {"max_actions": 500, "max_evaluations": 4},
  "own_command_history": ["pixel paint ...", "pixel fill ..."],
  "runner_feedback": {"ok": true, "exit_code": 0},
  "reward_feedback": {"overall": 0.42, "shape": 0.38, "text_match": 0.56}
}
```

この例は**Actorとの私的な学習I/O案**であり、Rust CLIに現存するコマンドの応答JSON形式を示すものではない。

### Actorに渡してはいけない情報

- 参照画像/生成PNGのバイト列、パス、URL、サムネイル、base64、画像埋め込み、VAE latent、画像トークン。
- 参照画像のピクセル一覧、RGB行列、差分ヒートマップ、画素座標ごとの正解色。
- 評価器が画像を見て作文した詳細な視覚説明や正解修正指示。
- 学習用画像を読み出すfile handle、プログラムから直接アクセスできるdataset mount。
- CLIの `pixel sample` / `import-image` 等を通した画素の読み取りや画像の取り込み（Actor向け許可リストから除外）。

評価器の数値スコアは目的を教えるために許可する。**画像の内容を文章で逐次教えるのは本設計に反する。** 複数のステージ別の数値を返す場合も、座標ごとの正解を推測できる細かさにしない。

実装時はActorとEvaluatorを別プロセス/権限に分離し、Datasetと生成PNGをActorからアクセス不能な場所に置く。入出力型テストと、参照/生成画像へのアクセスを拒否する負のテストを追加する。学習ログへの画像内容流出も監査する。

## 5. データセット（画像＋文章だけ）

学習前に画像1枚と対応説明1件以上をペアとして扱う。**元データに「描画手順」「コマンド列」「領域ごとの色ラベル」を必要としない**。下記metadataは管理用であり、Actorの入力ではない。

```json
{
  "sample_id": "sample-0001",
  "caption": "夜空に黄色い三日月",
  "reference_image": "evaluator-only/sample-0001.png",
  "group": "pixel64",
  "source": "licensed-dataset",
  "license": "verified",
  "split": "train"
}
```

- **64×64**: 64×64の元画像（または明示的な前処理基準で64×64に正規化した画像）と文章を使用。ピクセルパターン、シルエット、色数、エッジを重視する。透明背景と不透明背景を区別する。
- **高画質**: 目標画質に十分な元解像度を持つ画像と文章を使用。長辺、アスペクト比、画風、画質、画像内の主題の分布を管理し、学習目標ごとに評価解像度を固定する。
- train/validation/testを**作品・作者・出典・近似重複**で分離。類似構図や同じ画像の解像度違いが学習とテストにまたがらないようにする。
- 権利・利用条件・プライバシーを検証し、使用不可・出典不明データを収集しない。参照画像を学習サービス外へ公開しない。
- 訓練中に生じる「自分で作ったコマンド列＋スコア」は**ロールアウトログ**であり、教師データの新規入力形式ではない。ログは自己学習・再実行用に保存可能。
- 学習画像を64×64へ縮小する作業は**Dataset/Evaluator側の前処理**であり、Actorが画像を読むことではない。ただし正規化手順・色処理を固定して比較する。

## 6. コマンドの公開契約と描画プログラム

Dot Editor本体の正本はRust `pixel-cli`。現行の `rust/crates/hyper-dot-cli/src/command_table.rs` が公開コマンド定義を持つ。AIはその版で実在するコマンドだけを呼ぶ。

初期のActor向け許可候補（CLIの文法に基づく）:

| 役割 | Rust CLIコマンド例 | AIによる用途 |
| --- | --- | --- |
| ピクセル編集 | `pixel paint` / `pixel erase` / `pixel fill` | 形・色・透明度 |
| 解像度 | `canvas resolution set` | 全体グリッド変更 |
| 局所細分化 | `detail split` / `detail split-region` / `detail discard` | 必要な場所だけ詳細化 |
| レイヤー | `layer add` / `layer select` / `layer move` / `layer visibility` / `layer rename` | 背景・前景・部品を分離 |

`project new`、`project validate`、`export render` 等の準備/検査/保存はRunnerが担当し、Actorが任意のファイルを指定できない。CLI出力の読み取りは `status` 等の非画像メタデータに限定。**上表は許可候補であり、各コマンドの引数・存在は使用するRust版のコマンド表から自動生成した仕様（本体 #66）で確定する。**

Actorは生のshell文字列ではなく、例えば次のような**構造化コマンド列**を生成する（Dot Editor AI側の内部スキーマ案）:

```json
{
  "schema_version": 1,
  "ops": [
    {"cmd": "canvas.resolution.set", "args": {"width": 16, "height": 16}},
    {"cmd": "pixel.paint", "args": {"x": 4, "y": 5, "color": "#E33F45"}}
  ]
}
```

Runnerはこの構造を検査してから実際のCLI引数に変換する。これらのJSONキーは**未実装のAI用スキーマ案**であり、Dot Editor本体の既存CLI/保存JSONと混同しない。構造化した理由は、禁止コマンド・不正引数・shell注入を実行前に拒否し、行動確率と試行ログを安定して扱うため。

アクション1件ごとのプロセス起動・JSONの再読込は高解像度学習で負担になる。**#63 排他保存・revision検出を先に整え、#64 順序付き原子的バッチ編集を性能測定後に利用する**。同一バッチ内の順序と全体のロールバックを検証し、部分失敗で作品を壊さない。未知の描画APIや未実装の一括図形操作を、既存機能として扱わない。

**実行ログ**はモデルcheckpointの版、プロンプトID、seed、全コマンド、実行したCLIの版/hash、初期JSON、ステージごとのJSON hash、評価器版・数値評価、打ち切り理由を保存する。これにより人間が同じ画像を再生成し、ゲームエンジンからも同じプログラムを利用できる。

## 7. 学習ループと再試行

1. Trainerはペア `(caption, reference_image)` を選び、**captionだけ**をActorへ渡す。
2. Actorは目標スタイルと大まかな文章上の構図を計画し、次の編集コマンドを複数候補生成する。
3. Runnerが構文と制約を検査し、候補ごとに隔離された作品JSONへ編集を適用。失敗した候補は誤動作せず数値ペナルティとログを残す。
4. Runnerが保存した作品をPNGへ描画する（これは環境処理であり、ActorはPNGを観測しない）。
5. Evaluatorは**参照画像＋生成PNG＋caption**からスコアを計算。Actor/Trainerに画像は渡さず、数値スコアのみ返す。
6. Trainerは同一prompt/seedからの候補を比較し、スコアが高い候補を選び、変更に寄与した行動へ学習信号を割り当てる。
7. 良い状態をチェックポイントとして保持し、次の描画ステージへ進む。不正変更・性能悪化・予算超過では保存済み状態に戻す。
8. エピソード終了後、Actorを強化学習で更新する。別の未見画像・未見promptに対する評価を記録し、**訓練時の報酬上昇のみ**で改善と判定しない。

実装候補は、構文制約付きテキスト方策への方策勾配/グループ相対報酬学習、複数候補によるbest-of-N探索、段階別の行動選択である。**方式を初期段階で一つに固定せず、学習予算と再現性を比較して選ぶ。**

### 報酬の設計（提案）

```text
R = w_text * S_text_alignment
  + w_ref  * S_reference_similarity
  + w_form * S_structure_or_silhouette
  + w_style* S_style_or_palette
  - lambda_invalid * invalid_action_count
  - lambda_cost    * action_cost
```

- 重み、スケール、符号は **64×64 / 高画質で独立**に調整する。上式は定義案であり、確定ハイパーパラメータではない。
- `S_text_alignment`: 入力文と生成PNGの一致度。必要なら評価器内部のみ画像・テキスト特徴量を使用してよい。
- `S_reference_similarity`: 訓練時だけの参照画像に対する類似度。画像と文章の組から得られる複数の正解表現を不当に排除しないよう、単一指標へ過度に寄せない。
- `S_structure_or_silhouette`: 主題の全体形、輪郭、位置関係、エッジ等を段階別に評価する。座標別の正解はActorへ渡さず、集約スコアを返す。
- `S_style_or_palette`: 64×64では色数/パレット/ドット構造、高画質では局所構造/質感/破綻の少なさを重視。
- コマンドが不正な場合のハードゲート、ループ回避、不要な編集のコスト、誤操作によるデータ損失の監査を組み合わせる。

**画像と文章のCLIP系一致度だけを最大化すると、細部が不足した単純な画像でも高得点となるおそれがある。** 必ず構造/画質/人間の目視評価を併用し、報酬ハックを検知する。LPIPSなどの知覚距離は高画質の参考指標になり得るが、64×64ドット絵の画素単位の差には必ずしも最適ではない。指標の採否は小規模な人間評価との一致率で決める。

## 8. 二つの独立モデル

### 8.1 Pixel64（64×64ドット絵）

- 作品の**論理解像度/最終書き出しのネイティブ解像度を64×64**とする。512×512への最近傍拡大は鑑賞用であり、学習時の64×64の定義を変えない。
- カリキュラム案: 4×4/8×8で配置 → 16×16で輪郭 → 32×32で形の整合 → 64×64で色・細部。ステージ間は細部保持を基本とし、明示した範囲以外は破棄しない。
- ピクセル精度だけでなく、シルエット、色数、重なり、ドット絵としての読みやすさを測る。小さな色違いが意味を持つため、一般写真用知覚指標だけで判定しない。
- データ: 64×64ドット絵と対応文章（作品/作者単位で分割）。必要に応じて背景色・透過の取り扱いを固定する。
- 受入観点: 未見文章に対する主題の識別可能性、正確な解像度、コマンドのみで再生できること。

### 8.2 HighRes（高画質画像）

- データ: 高解像度の画像と対応文章。Pixel64とは**別のモデル重み・データセット・評価基準・checkpoint**を持つ。
- カリキュラム案: 8/16/32/64で構図 → 128/256で形状 → 512以上で局所質感・影・微細要素を編集。**目標ネイティブ解像度は実験で決める**（例: 256×256、512×512）。
- 高解像度化後に何を描き足すかをActorが学ぶ。**拡大コマンドだけで高品質になるとは保証しない**。
- 透明度、階調、グラデーション、領域のまとまりは使える編集コマンドから実現する。滑らかさを必要とする表現については、現在のDot Editorの描画/書き出し能力をベンチマークする。
- 同じテキストに複数の妥当な画像があり得る。参照一枚への厳密一致より、テキスト適合、構図、ディテール、人間評価、破綻の少なさを重視。
- 受入観点: 見た目の品質、解像度に応じた**新しい細部の増加**、コマンド数/実行時間、未見プロンプトへの一般化。

二つは推論APIの入口とコマンド文法の管理コードを共有してよい。ただし**単一モデルのモード切替だけ**をもって「別モデル」とはしない。

## 9. 精度を上げるための優先提案

| 優先 | 提案 | 狙い | 確認実験 |
| --- | --- | --- | --- |
| A | **粗い構図から細部へ進む階層カリキュラム** | 長い描画手順の学習難度を下げ、構図崩れを抑える | いきなり64×64 vs 4→8→16→32→64 |
| A | **完成時だけでなくステージごとに数値報酬** | 何が改善に寄与したかを学習しやすくする | 最終報酬のみ vs 段階報酬 |
| A | **同じ文章から複数候補を生成し比較、最良チェックポイントから再試行** | 画像を見ずに探索効率を上げる | 1候補 vs K候補（同じ実行予算） |
| A | **構文制約付きの操作DSLとCLIバッチ編集** | 無効コマンドを減らし、画像1枚当たりの実行回数を削減 | 自由テキストコマンド vs 型付きコマンド |
| B | **意味・輪郭・色・知覚画質の複合評価** | 画像と無関係な報酬上昇や細部不足を抑える | 単一指標 vs 複合指標＋人間評価 |
| B | **文章の中間計画（前景/背景/主要物/色/順序）** | 視覚入力なしでも長い操作を整理 | 直列コマンド vs テキスト計画付き |
| B | **段階ごとの局所分割と保存/ロールバック** | 形を崩さず局所細部を編集 | 全面一律高解像度 vs 局所分割 |
| C | **一般的な図形・領域一括操作の本体側拡充** | 高解像度での単一画素操作の膨大さを緩和 | 現行コマンド＋batch vs 汎用図形操作追加 |

「A」は最初の小規模検証から入れる。「B/C」は実測で効果が出たものだけ採用。図形コマンドを追加する場合はAI専用抜け道ではなく、人間/ゲームエンジンでも利用できる一般のDot Editor操作として別の本体Issueで設計する。

## 10. 実現性・品質ゲート

まず**簡単な構図をコマンドだけで学べるか**を検証する。未見文章・未見画像へ一般化しない場合、巨大な高画質モデル学習へ進まない。

| 段階 | 最小課題 | クリア条件 |
| --- | --- | --- |
| PoC-0 | Rust CLIの操作・再生・出力 | 許可されたコマンドだけで作品JSON/PNGを再現し、視覚情報がActorへ流れない |
| PoC-1 | 単色図形・2色・簡単な物体、低解像度 | ランダム方策/固定テンプレートを超える未見テキストの評価改善 |
| PoC-2 | 未見の64×64ドット絵 | ステージ評価・候補探索の効果、対象物の分かりやすさを人間にも評価 |
| PoC-3 | 高画質モデルで128→256等の細部追加 | 解像度だけ上げた基準画像に対する知覚品質・意味一致・細部追加の改善 |
| 製品化 | 本体の実配布CLI利用、失敗復旧、予算管理 | 再現可能な作品生成と品質・コスト・可用性の受入基準を満たす |

具体的な達成閾値はPoC-1の基準測定後に設定する。**訓練で見た画像への類似度やコマンド成功率だけで「文章から絵を描ける」と判定しない。** スコアを固定した評価器の学習用とテスト用の分離、checkpointの比較、3 seed程度の再現試験、人間によるblind比較を推奨する。評価器を調整する場合、旧評価器に対する結果も保存する。

## 11. 性能・セキュリティ・障害時の動作

- Actorが出せる操作はallowlistで固定する。path/任意shell/`--import-image`/外部URL/任意コード実行は拒否する。
- CLIは固定された一時作業ディレクトリと制限された権限で実行する。編集可能な作品を候補ごとに分離し、既存作品の破壊的上書きを禁止する。
- 1候補の最大アクション数、最大CLI呼出し、最大解像度、キャンバス/レイヤー数、CPU/メモリ、最大評価回数を設定する。数値はPoCで計測して決定する。
- 同時編集は本体 #63 のロックとrevision契約に従う。ステージ単位で原子的に保存し、失敗候補は戻して次を試す。
- 高解像度ではアクション数と計算量が急増するため、#64のbatchや一般図形操作が実際に有効かプロファイルし、未実装の場合はPoCの解像度を制限する。
- 未許可操作はデータ保存前に拒否し、AIへ数値ペナルティ/エラーだけ返す。評価器の失敗は「低画質」とみなさず**評価失敗**として再試行可能に分類する。
- 対応CLIの版、モデル版、評価器版、seed、各スコア、実行時間、実行したコマンドを追跡可能にする。
- 表示向けプレビューを人間に見せることは許されるが、Actorへ返す観測からは切り離す。
