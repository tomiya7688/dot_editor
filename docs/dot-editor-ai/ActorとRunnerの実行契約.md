# Dot Editor AI — ActorとRunnerの実行契約 v0.2

> 状態: P4の**詳細設計案**（未実装） / 2026-11-04 / 親Issue [#69](https://github.com/tomiya7688/dot_editor/issues/69)  
> 対象: 生成モデルの開発者、Rust CLI連携担当、検証担当。  
> 上位仕様: [設計書](設計書.md)。本体の実際のコマンド仕様は、対象版のRust CLIとその生成コマンド表（本体 #66）を正本とする。

## 1. この設計の目的

入力文章から**Dot Editorの編集コマンドを組み合わせて**作品JSONとPNGを作る。元の学習データは画像と対応する文章だけで、正解コマンド列を与えない。生成モデル（以下 **Actor**）は、参照画像も自分の描いた画像も**一度も観測しない**。

評価器は画像を読み、Actorには**制限された数値評価**を返す。評価器とActorは同じモデル、同じプロセス、同じファイル権限に置かない。AI本体の実装はDot Editor本体v1完成後の別リポジトリで行う。

- **確定要件**: 画像非参照、テキスト入力、編集コマンドによる描画、外部評価、64×64/高画質の別モデル。
- **実装案**: 次項以降のJSONプロトコル、リトライ回数、失敗コード、状態機械。採用前にPoCと設計レビューが必要。
- **非目標**: 画像を生成する別モデルからピクセルを転写すること、画像→操作列を教師データとして逆算すること、Actorから画像を直接読み出すこと。

## 2. 信頼境界（重要）

| 境界 | 保持できるもの | Actorへ渡せるもの |
| --- | --- | --- |
| Dataset/学習データ領域 | 参照画像、文章、著作権/重複情報 | **文章だけ**。画像の名前・パスや中身は渡さない |
| Actor | 入力文章、固定コマンド文法、自己操作履歴、非画像メタデータ、評価結果 | 自分が発行した操作と、数値報酬 |
| Validator/Runner | 構造化操作、隔離作業領域、作品JSON、CLI実行結果、描画中間成果物 | 許可された**成功/失敗コードと操作状態のみ** |
| Evaluator | 参照画像、生成PNG、文章、採点器の内部視覚特徴 | **事前に決めた集約数値**だけ |
| Trainer | 軌跡、Actorの行動確率、評価数値、checkpoint | Actorへの訓練信号。画像や画像表現は転送しない |
| 人間向けViewer | 生成PNG、編集履歴、作品JSON | 画像は人間に表示可能。ViewerとActorを切り離す |

### 画像非参照の定義と限界

禁止: 画像バイト列、画像トークン、画素表/座標色一覧、参照/出力画像のパス、画像埋め込み、差分画像、領域ごとの正解色、画像から自動生成した修正文章。**自分で描いた画像もActorへ渡さない**。

許可: 初期キャンバスの寸法、レイヤー名、現在の論理解像度、選択中レイヤー、Actor自身が発行したコマンド、コマンドの構文/境界エラー、制限された数値評価。画素読み取り用の `pixel sample` や画像 `import` はActorから実行禁止。

**数値報酬自体は画像由来の間接情報**である。無制限の高精度評価クエリを許せば理論的に画像情報を復元し得るため、「どんな情報も一切得ない」とは主張しない。画像を直接観測させないという確定制約を守りつつ、スコアの解像度・評価回数・項目数を制限する。

## 3. モジュールと所有権

| モジュール | 所有する責務 | 所有しない責務 |
| --- | --- | --- |
| DatasetService | 文章/参照画像の対応、split、権利・隔離 | Actorへの画像配信 |
| Actor（Pixel64/HighRes） | 文章から編集操作を選択する確率方策 | PNG表示、画像ファイルI/O、任意shell |
| Validator | 許可コマンド・引数・範囲・アクション予算の検査 | 画質の評価 |
| Runner | Rust CLI起動、原子的操作、仮想キャンバス状態の記録、保存・復旧 | 次の色や座標の提案 |
| Evaluator | 参照/生成画像と文章に基づく報酬計算 | コマンド生成とActorへの画像送信 |
| Trainer | 候補比較、方策更新、ログとcheckpointの再現性 | ピクセルを描くショートカット |
| Viewer | 人間向けの結果表示・書き出し | Actorへの観測供給 |

Controller（TrainerまたはInferenceService）が処理順を管理する。Actorにファイルシステムやネットワークの任意アクセスを与えず、**専用の型付き入出力**だけを接続する。

## 4. Actorへの観測スキーマ案

以下は**Dot Editor AIの内部プロトコル案**であり、現在の `pixel-cli --json` の出力ではない。

```json
{
  "schema": "dot-ai.observation.v1",
  "episode_id": "opaque-001",
  "prompt": "白い背景、赤いりんごが1個",
  "mode": "pixel64",
  "stage": "shape",
  "catalog_id": "rust-pixel-cli-version-and-sha",
  "canvas": {"width": 16, "height": 16, "selected_layer": "main"},
  "budget_remaining": {"actions": 128, "evaluations": 3},
  "history": [
    {"action_id": "a1", "command": "pixel.paint",
     "args": {"x": 4, "y": 5, "color": "#CC2233"}, "accepted": true}
  ],
  "last_feedback": {
    "execution": {"status": "ok", "reason_code": "NONE"},
    "reward": {"score_bucket": 6, "scale": 10}
  }
}
```

**必須の検証**: `episode_id` は画像ファイル名でなくランダムな識別子。 `history` は自分が送ったコマンドだけ。 `canvas` はコマンドから決まる編集状態であり、画像特徴量ではない。 `score_bucket` は評価器側で丸めたスコアで、細かな座標や修正文章を含まない。

初期PoCは**総合スコア1個のみ**を既定とする。ステージ別スコアを追加するときは項目数・精度・回数上限を固定し、参照画素を復元できないか検証する。

## 5. Actorの行動スキーマ案

```json
{
  "schema": "dot-ai.action.v1",
  "catalog_id": "rust-pixel-cli-version-and-sha",
  "base_revision": "runner-owned-revision",
  "ops": [
    {"command": "pixel.paint",
     "args": {"x": 4, "y": 5, "color": "#CC2233"}},
    {"command": "pixel.paint",
     "args": {"x": 5, "y": 5, "color": "#CC2233"}}
  ],
  "decision": "continue"
}
```

- `decision` は `continue` / `finish_stage` / `finish_image`。コマンドでない意思決定フィールドで、描画の抜け道にしない。
- `ops` は**順序付き**。Runnerは全件を検証してからCLIに送る。1件も有効でない、順序不正、座標範囲外、未知キーや想定外の引数は書き込み前に拒否する。
- 色は `#RRGGBB` またはCLIが明示的に認める形式に限定。任意式、ファイル、URL、shell展開を受け付けない。
- 座標は**現在の論理キャンバスの0起点整数**。解像度変更や細分化後は新しいコマンド表と解像度から、次の操作の範囲を再検査する。
- **最終成果物はDot Editorの実コマンド列**。AI側の構造化形式はそのコマンドへの型付き表現にすぎず、Rust Coreを直接書き換えない。

### 許可コマンド（初期案）

| 分類 | Actorが選べる | Runnerだけが行う |
| --- | --- | --- |
| 通常描画 | `pixel paint`, `pixel erase`, `pixel fill` | `pixel sample` は禁止 |
| 解像度 | `canvas resolution set` | 新規プロジェクトの安全な初期化 |
| 細分化 | `detail split`, `detail split-region`, `detail discard` | 細部破棄前の復旧点作成 |
| レイヤー | `layer add/select/rename/move/visibility` | 入出力パス・ファイルの所有 |
| 検査・出力 | **なし**（Actorには構造化状態だけ） | `project validate`, `status`, `export render` |

`project new`、`export render`、`--project`、`--output`、`--force` などのファイル操作権限はRunnerだけが持つ。`pixel sample` が自分で塗った色を読む用途でも、画像非参照の監査を単純化するためActorには与えない。存在しない `rectangle` や `gradient` のCLIを既存機能として扱わない。

**同一プロセスで複数コマンドを原子的に送る機能は本体 #64 の設計/実装待ち**。それまでは1呼び出し1操作で一時複製を用い、全体を一つの成功として扱う。#63（revision/排他）の完了を前提とし、現在のCLIが既にバッチ/競合制御を持つとは仮定しない。

### 高水準マクロの扱い

コマンド数削減のために、将来「線」「矩形」「円」などを**既存のpixel paint等の列へ決定的に展開する内部マクロ**を検討してよい。初期PoCでは無効化し、ネイティブ操作のみをベースラインにする。採用するときも展開結果を全て記録し、画像を直接注入しない。新しいネイティブ描画機能が必要ならDot Editor本体の通常Issueで設計する。

## 6. 実行の状態機械

```text
NEW
  → INIT       : Runnerが作品を初期化し、参照画像とは別の領域へ保存
  → PROPOSE    : Actorが文法に沿うopsを生成
  → VALIDATE   : Validatorが全件を検査。失敗なら編集しない
  → EXECUTE    : Runnerが候補専用コピーへRust CLIを実行
  → SNAPSHOT   : 成功時に作品JSONを原子的に確定
  → RENDER     : RunnerがPNGを生成（Actorには渡さない）
  → EVALUATE   : Evaluatorが画像比較。数値スコアのみ返す
  → SELECT     : ステージ予算内の候補から採択/復旧/再試行
  → NEXT_STAGE : 固定カリキュラムの次段へ
  → COMPLETE   : JSON/PNG/操作列を保存、人間へ表示
  → FAILED     : 回復不能/予算上限/評価器障害
```

- 初期値、レイヤー、透明/不透明の扱い、作品寸法、評価解像度は**同一エピソード中固定されたルール**に従う。
- 候補はすべて直前の**同一の基準snapshot**から作成する。比較中に候補同士が共有作品JSONへ書き込まない。
- 評価を呼ぶ前に `project validate` と出力寸法検査を行う。実行エラー・構文エラーは画質スコアとは区別する。
- 採択候補と非採択候補を分けて記録し、最良状態への復元は**編集コマンドのUndo頼みでなく保存済みsnapshotの複製**で行う。別CLIプロセス間でUndo履歴は共有されない。
- 品質が単調増加するとは限らない。最初は「最良スコアを保持する」簡易探索とし、学習の探索的悪化を許す手法は別途比較する。
- Actorは**最後の実行後の画像ではなく、最後の実行成否と数値スコアだけ**を受け取る。

### エラー分類と返却

| 区分 | 例 | Actorへの返却 | Runnerの動作 |
| --- | --- | --- | --- |
| `INVALID_ACTION` | 未知コマンド・予算超過 | 固定コード・失敗 | 一切実行しない |
| `OUT_OF_BOUNDS` | 無効座標・解像度 | 固定コード・失敗 | 書き込みせず再提案可能 |
| `REVISION_CONFLICT` | 競合変更 | 固定コード・失敗 | 再読込/独立候補へやり直し |
| `CLI_FAILURE` | プロセス異常・保存失敗 | 固定コード・失敗 | snapshot保持、異常ログは運用者のみ |
| `EVALUATION_UNAVAILABLE` | 採点器が落ちた | **報酬なし** | 候補を罰せず評価を再試行/停止 |
| `BUDGET_EXHAUSTED` | 時間/呼出し上限 | 固定コード・終了 | 最良の検証済み作品を返却 |

生の `stderr`、パス、画像のhash、評価器の詳細メッセージをActorへ直接流さず、Runnerで上記コードへ正規化する。ユーザーには処理失敗の説明と、利用可能な復元済み作品を提示する。

## 7. 学習時と推論時の差分

| 項目 | 学習時 | 推論時 |
| --- | --- | --- |
| 入力 | (文章 + 参照画像) はDatasetで管理、Actorには文章のみ | ユーザー文章のみ |
| 画像比較 | Evaluatorだけが参照画像と生成PNGを比較 | **参照画像は存在しない**。生成PNGと文章による独立評価を利用してよい |
| Actor | 操作履歴と有界な評価数値だけ観測 | 同じ契約を守り生成PNGも見ない |
| 更新 | エピソード終了後に重み更新可 | **重みを固定**し、候補選択のみ |
| 出力 | 訓練ログ、モデルcheckpoint、作品 | ユーザー向け作品JSON、操作列、PNG |

**推論時には参照画像類似度のスコアを計算できない。** 学習で得た品質指標と推論時の指標は別に定義する。同じ名前のスコアを無理に流用しない。

## 8. 予算・性能と再現性

- `max_actions`: ネイティブ編集操作数。許可マクロの展開後の実操作を数える。
- `max_cli_calls`: subprocess呼び出し数（#64実装前後の比較用）。
- `max_evaluations`: 画像を読むEvaluatorへの問い合わせ数。情報流出の制限も兼ねる。
- `max_steps`/`max_wall_time`/`max_memory`/`max_resolution`: 操作数・時間・メモリ・高解像度の上限。実測前に値を固定しない。
- 64×64は4,096セル、512×512は262,144セル。1セルずつの描画なら最大操作数の規模は**64倍**。高画質は一律に全画素を塗る案ではなく、粗→細、領域フィル、層、局所分割、可能なら一般図形操作を評価する。
- ログは `actor_model_hash`、`command_catalog_hash`、`CLI_binary_hash`、`evaluator_hash`、`dataset_split_id`、seed、正規化ops、状態遷移、スコア、snapshotのhashを保持。参照画像の**実パスや画素**はActorログへ保存しない。
- PNGと作品JSONの検証はRunnerのみ。ステージを跨ぐ再現試験は「コマンド再生→作品JSONの意味的同等性→PNGの一致」を確認し、保存JSONのキー順まで一致させる必要はない。

## 9. 必須受入テスト（設計段階の計画）

- **境界テスト**: Actorプロセスに画像、画像パス、PNGバイト列、画像特徴量、画素データを与えようとすると拒否される。
- **CLI拒否テスト**: `pixel sample`、画像import、任意shell、未知フラグ、パス引数、過大座標・解像度が実行前に拒否される。
- **観測漏えいテスト**: 生成PNG、stderr、評価器例外、ファイル名、画像hashがActorの観測/学習ログに現れない。
- **リワード制限テスト**: 評価上限・スコア量子化・項目上限が、失敗時も適用される。評価器障害を低画質報酬へ混ぜない。
- **原子性テスト**: ops途中失敗・競合更新・プロセス終了・保存失敗でも、採択済み作品とrollback snapshotが失われない。
- **再現テスト**: 同じCLIバージョン・初期作品・コマンド列を再生した結果が意味的に一致する。
- **モデル分離テスト**: Pixel64とHighResの重み、checkpoint、学習/評価split、予算設定が混在しない。
- **製品境界テスト**: AI側の依存パッケージをインストールせず、本体Rust CLI単体で全既存E2Eが動く。

以上は**実装時に追加するテストの仕様**であり、現時点で実行成功したことを意味しない。
