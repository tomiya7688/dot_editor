# ワンクリック起動確認と確認手順の詳細設計

対象: [Issue #113](https://github.com/tomiya7688/dot_editor/issues/113)。関連: [#67](https://github.com/tomiya7688/dot_editor/issues/67)（起動時間・メモリの実測）、[#26〜#30](https://github.com/tomiya7688/dot_editor/issues/26)（実機の操作確認）、[#108](https://github.com/tomiya7688/dot_editor/pull/108)（測定スクリプト）。利用者向けの手順は[起動確認の手順](../起動確認の手順.md)です。状態: **実装済み**（確認した日付: 2026-11-06、範囲: 窓を作らない確認と、確認結果の記録。実際の窓を使う確認は、この設計では人が目で行う）。

## 背景・目的・入口

#108で測定スクリプトを追加しましたが、利用者が「どのコマンドを打ち、何を見て、結果をどこへ書くか」が分からず、実機での確認が進みませんでした。そこで、**ダブルクリック1回**で確認を始められ、**目で確認する項目が画面に順に出る**入口を用意します。

利用者の入口は、リポジトリ直下の`起動確認.bat`をダブルクリックすることだけです。

## 現状

| 項目 | 現状 | 確認 |
| --- | --- | --- |
| 窓を作らない確認 | `python src/dot_editor.py --smoke-test`で、Tclとバックエンドの基本処理を確かめられる | ソースで確認（`main`関数） |
| 起動時間・メモリの測定 | `scripts/measure_gui_startup.py`が、新しいプロセスで窓を作って測る。窓を作れない環境では「未実行」（終了値2）になる | #108のテストとこのPCでの実行で確認 |
| 実際の窓の目視 | 手順がなく、各Issueに「実機で確認」とだけ書かれていた | 今回の設計で手順化 |
| このPC（開発用）の窓 | `tk.Tk()`が10秒以上応答せず、測定は未実行。利用者のPCでは未確認 | 2026-11-06に実行して確認 |

## 利用者の流れ

| 順 | 画面に出ること | 利用者がすること |
| --- | --- | --- |
| 1 | 環境（Python、OS、Tk）を表示 | 見るだけ |
| 2 | 自動確認A: 窓を作らない確認の合否 | 見るだけ |
| 3 | 自動確認B: 3回の起動で測った時間とメモリ | 見るだけ（数十秒かかる） |
| 4 | 実際の窓が開く。続けて確認項目を1つずつ表示 | 窓を見ながら、`y`（はい）、`n`（いいえ）、`s`（試せない）を入力してEnter |
| 5 | 結果を`起動確認の結果.txt`に保存したと表示 | 結果の中身をIssueへ貼る（貼り先は手順書に書く） |

自動確認が失敗または未実行のときは、手順4を行わず、原因と次にすることを日本語で表示します。

## 契約

### 終了値

| 値 | 意味 |
| --- | --- |
| 0 | 自動確認がすべて成功し、目視確認に`n`がない（`s`は成功に数えず、結果に「試せなかった」と残す） |
| 1 | 自動確認の失敗、または目視確認に`n`がある |
| 2 | 窓を作れず、確認できなかった（未実行。成功扱いにしない） |

### 結果ファイル（`起動確認の結果.txt`、UTF-8）

日時、Python、OS、各確認の結果、測定値（中央値と最大）、目視確認の答え、総合判定を、1項目1行で書く。利用者の個人情報や作品の中身は書かない。リポジトリには含めない（`.gitignore`）。

### 部品の責務

| 部品 | 責務 | 窓に依存するか |
| --- | --- | --- |
| `起動確認.bat` | Pythonを探して`scripts/startup_check.py`を起動し、終了前に一時停止する | しない |
| `scripts/startup_check.py` | 確認を順に行い、結果を表示・保存する。表示と入力は関数に分け、テストでは差し替える | 窓を開くのは手順4だけ |
| `scripts/measure_gui_startup.py` | 起動時間とメモリを測る（#108。変更しない） | する |

## 失敗時の扱い

| 状況 | 表示と記録 | 終了値 |
| --- | --- | --- |
| Pythonが見つからない（bat） | 「Pythonが見つかりません。インストール後にもう一度実行してください」 | 2 |
| `--smoke-test`が失敗 | 失敗した理由（標準エラーの末尾）を表示し、窓の確認へ進まない | 1 |
| 窓を作れない（測定が未実行） | 「この画面では窓を開けませんでした。デスクトップに接続したWindowsで実行してください」 | 2 |
| 目視で`n` | 該当項目名を結果に残し、Issueに貼って報告するよう案内 | 1 |
| 結果ファイルを書けない | 画面にだけ結果を出し、書けなかったと表示 | 総合判定に従う |

## 検証

| 確認 | 方法 | 種類 |
| --- | --- | --- |
| 総合判定の規則（0/1/2） | 単体テストで結果の組み合わせを与える | 自動 |
| 入力`y/n/s`の解釈と不正入力の再入力 | 入力関数を差し替えた単体テスト | 自動 |
| 結果ファイルの内容 | 単体テストで一時フォルダに書かせ、必要な行を検査 | 自動 |
| 実際の窓と項目の目視 | 利用者がWindowsで`起動確認.bat`を実行 | **人**（この設計では自動化しない） |

## 実装の順序・受け入れ条件

1. 設計書、手順書、設計書一覧へのリンク（このPR）。
2. `scripts/startup_check.py`と単体テスト、`起動確認.bat`、`.gitignore`（このPR）。
3. 利用者のWindowsで実行し、結果を#67と#26〜#30へ貼る（所有者または利用者）。

Issue #113の完了条件との対応: ワンクリック起動と結果保存=`起動確認.bat`と結果ファイル、窓を開けない場合の扱い=失敗時の表、手順書=[起動確認の手順](../起動確認の手順.md)、設計書の一覧からのリンク=本書、単体テストとCI=検証の表。

## 未決・リスク・対象外

- 目視の項目は「窓が開く、メニューが読める、塗れる、保存できる、ヘルプが開く」の最小限です。キーボード操作の通し確認（#26〜#30）は項目が多いため、別の手順（Issue #30のテンプレート）に残します。
- 起動時間の「許容値」は決めていません。変更前後の比較で、明確な劣化がある場合に改善または根拠を記録します（#67）。
- 配布版の実行ファイル（EXE）での確認は、署名方式（#55）の決定後に、別の手順として追加します。
