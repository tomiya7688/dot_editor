# 最終成果物と出所の検証

## 背景・目的・現在の制限

対象はHyper Dot Editorの配布物を利用する方です。ファイルの取り違え・改変と、別の作成元によるファイルを区別するため、最終成果物のSHA-256とGitHub Actionsの署名付き出所情報（attestation）を照合します。hashの一致だけでは作成元を証明できません。

現在はWindowsのAuthenticode署名・RFC 3161 timestampが未実装のため、成果物のアップロードを停止しています。CIでattestationが成功しても、Windows署名や公開許可の完了とは扱いません。以下は公開再開後に取得したファイルを確認する手順です。ローカルで作成しただけのファイルには、GitHub CIのattestationはありません。

## 現行ビルドが扱う一覧

| 最終成果物 | 生成元 | この段階の検証 | 残る配布条件 |
| --- | --- | --- | --- |
| `HyperDotEditor-windows-x64.zip` | Windowsビルド・配布スモーク後の圧縮 | ZIP全体のSHA-256とattestation | 内部のEXE・DLL・PYDの署名方針とAuthenticode検証 |
| `hyper_dot_editor-<版>-py3-none-any.whl` | Pythonのパッケージビルド | wheelそのもののSHA-256とattestation | 公開gateの完成 |
| `hyper_dot_editor-<版>.tar.gz` | Pythonのソース配布ビルド | sdistそのもののSHA-256とattestation | 公開gateの完成 |
| `SHA256SUMS` | 上の3成果物から生成 | manifest自身のattestation | 上記すべての検証 |

`dist/windows` はZIPに含める作業用ディレクトリであり、単独の公開成果物ではありません。Rust CLI・macOS・Android・コンテナの公開経路は現行ビルドにはありません。追加時は一覧と署名方式を別途整備します。既存GitHub Actions artifactはまだ監査・再署名しておらず、新しい検証の成功を過去の配布物へ適用しません。

## 利用者の確認手順

GitHub CLIの`gh attestation verify`が使える環境を用意してください。ダウンロード先で、まずmanifestの作成元を確認してください。

```powershell
gh attestation verify .\SHA256SUMS --repo tomiya7688/dot_editor --signer-workflow tomiya7688/dot_editor/.github/workflows/ci.yml --source-ref refs/heads/main --deny-self-hosted-runners
```

次に、利用する成果物そのものも同じ制約で確認してください。例えばWindows ZIPの場合は次のとおりです。wheel・sdistを利用する場合は、対象ファイル名を置き換えてください。

```powershell
gh attestation verify .\HyperDotEditor-windows-x64.zip --repo tomiya7688/dot_editor --signer-workflow tomiya7688/dot_editor/.github/workflows/ci.yml --source-ref refs/heads/main --deny-self-hosted-runners
Get-FileHash .\HyperDotEditor-windows-x64.zip -Algorithm SHA256
```

表示されたhashを、検証済み`SHA256SUMS`の同名行と比較してください。期待するソースSHAが分かる場合は、検証コマンドへ`--source-digest <期待するコミットSHA>`も付けてください。終了コードが非0、ファイル名やhashが不一致、期待する作成元でない場合は、その成果物を使用しないでください。未署名ファイルを実行して動作確認することで検証を代用しないでください。

## CIとローカル生成の違い

Windowsビルドは、最終3成果物の欠落・空・重複版・版の不一致・不明なトップレベルファイル・symlinkを拒否し、`dist/SHA256SUMS`を原子的に生成します。専用の`dist`へ別の成果物を混ぜないでください。既存ファイルがあるため失敗した場合は、内容を確認して保管先を分けてから再ビルドしてください。

ローカルで生成済みの成果物を確認する場合は、ソース側で次を実行してください。これはhashと一覧の一致だけを検査し、署名の確認やネットワークへの送信は行いません。

```powershell
.venv/Scripts/python.exe scripts/artifact_checksums.py dist --check
```

CIではpushイベントだけでOIDCを使用し、4成果物へ出所情報を付与します。同じジョブでbundleの署名、repository、workflow、ソースSHA・ref、GitHub-hosted実行を検証し、どれかが失敗すれば停止します。PRイベントでは書込権限が制限されるためattestationを作成せず、マージ前に同じHEADのpush側検証も確認します。成果物のアップロードは引き続き停止します。

方式の根拠は[GitHubのattestation手順](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)、検証条件は[GitHub CLIの公式説明](https://cli.github.com/manual/gh_attestation_verify)を参照してください。
