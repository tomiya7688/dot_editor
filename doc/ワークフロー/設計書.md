# 設計書の書き方（Issueから実装の前に）

## 背景と目的

Issueに「何が欲しいか」は書かれていても、「どういう形で作るか」「何をもって完了か」が決まっていないまま実装すると、あとから仕様の食い違いが見つかり、作り直しになります。実装の前に設計書を置き、実装担当・レビュアー・利用者が同じ前提で話せるようにします。利用者の直接操作はありません。実装担当（`implementer`）が、対象のIssueに設計書がないときに書きます。

## いつ書くか

| 状況 | 行うこと |
| --- | --- |
| 対象のIssueの設計書が[設計書の一覧](../../docs/design/README.md)にある | 読んで従う。食い違いを見つけたら、実装を変える前に設計書を直す |
| ない | 先に設計書を書き、一覧に追加して、設計だけのPRとして出す（実装と同じPRでもよいが、設計の節を先に確定する） |
| 1画素の修正や、表現の直しなど、仕様に影響しない小さな変更 | 設計書は不要。Issueと自己レビューの記録で足りる |
| 契約（CLIの引数、保存形式、エラー種別名）が変わる | 必ず設計書と、契約の正本（[CLI契約](../../docs/CLI契約.md)など）を同じPRで直す |

## 置き場所と名前

- 場所: `docs/design/<英小文字とハイフン>.md`。複数のIssueをまとめてよい（同じ部品・同じ契約を扱うとき）。
- 一覧: [設計書の一覧](../../docs/design/README.md)に、Issue番号・内容・状態を1行足す。一覧にない設計書は検査が失敗します。
- 将来のアプリなど、別の領域は専用のフォルダ（例: `docs/dot-editor-ai/`）を使い、一覧からリンクする。

## 構成（この順で書く）

```markdown
# <対象>の詳細設計（未実装）           ← 状態を題名に入れる（実装済みなら省く）

対象: [Issue #N](https://github.com/tomiya7688/dot_editor/issues/N)。正本の契約へのリンク。状態: 設計案／実装済み。確認した日付と範囲。

## 背景・目的・入口        ← 誰の何の問題か。利用者が最初に行う操作（コマンド、画面、ファイル）
## 現状                    ← 今どうなっているか（ソースで確認した事実。確認していないことは「未確認」）
## 契約／仕様              ← 入力、出力、状態、キー、ファイル形式。表で書く
## 流れ／部品の責務        ← 順序、部品の分担、データの持ち主
## 失敗時の扱い            ← エラーの種別、途中失敗で何を保つか
## 検証                    ← どのテストで何を確かめるか（自動と、人が行う確認を分ける）
## 実装の順序・受け入れ条件 ← PRの分け方、各PRの完了条件、Issueの完了条件との対応
## 未決・リスク・対象外    ← 決めていないこと、所有者の判断が要ること、扱わないこと
```

## 守ること

1. **現状と案を混ぜない。** 実装していない機能を、現行の挙動のように書かない（[CLI契約](../../docs/CLI契約.md)の「次期拡張」と同じ扱い）。確認していない事実は「未確認」と書く。
2. **利用者の入口から始める。** 「どのコマンドを打つ／どのキーを押す／どのファイルを開く」と、その結果から書く（R19）。
3. **表を使う。** 比較、一覧、対応表は表にする。図が必要なときはmermaid。実装から自動生成した図だけで設計意図を代用しない。
4. **主語と文末を合わせる。** 利用者の操作は依頼形（「実行してください」）、アプリの動作は説明形（「保存します」）（R18）。用語は初出で説明し、同じ概念に同じ語を使う（R20）。
5. **Issueの完了条件と対応させる。** 完了条件を表にして、それぞれをどの確認で満たすか書く。満たせない条件は、そう書く。
6. **所有者の判断が要ることを隠さない。** 費用・契約・保護設定・過去の成果物の削除などは「所有者の判断が必要なこと」に分けて書き、担当者が決めない。
7. **既存の契約を壊さない。** 終了値、エラー種別名、JSONのversionなど外部から見える約束は、変更するなら理由と移行を書く。
8. **担当者向けの手順をREADMEに入れない。** 設計書は`docs/design/`に置き、READMEには利用者向けの説明だけを置く。

## 書き終えたら

自己レビューで次を確認し、結果をPRの本文に1行で書きます。

- [ ] 一覧に追加した。リンクが実在する。
- [ ] 現状の記述に、確認した日付と範囲がある。
- [ ] 失敗時と、確認方法（自動と人の確認）が書いてある。
- [ ] 他の設計書・契約と矛盾しない（同じ用語、同じ名前、同じエラー種別）。
- [ ] 実装を始められる粒度（PRの分け方と完了条件）になっている。
