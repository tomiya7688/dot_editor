# 1回の作業ワークフロー

この文書は、1つの機能単位または修正単位を完了するまでの作業手順を定義する。

作業前とレビュー時は、共有する [コーディング規約](../../コーディング規約.md) のR01〜R20を確認する。ローカルに `レビュー基準.md` がある場合は確認表として使用するが、存在しない環境でも共有規約を適用する。違反は差し戻し、必要な確認を実施できない場合は判定保留とし、修正と再検証が終わるまで受け入れ済みにしない。

1. 作業開始前に作業ツリーを確認する。自分の作業と無関係な変更は変更・削除しない。
2. リモートの変更を取り込む。git fetch origin の後、現在の作業ブランチへ origin/main を fast-forward またはマージし、最新の共有状態を基準にする。
3. 開発予定と関連する仕様・評価フィードバックを確認し、今回完了する1つの作業単位を決める。関連するPRは開いているものだけでなく、差し戻し・未マージで閉じられたものも確認し、レビュー、行コメント、会話欄の指摘と対応状況を読む。指摘本文が取得できない場合は未確認と明記する。
4. 実装する。UI、処理、データ保存の責務を混在させず、既存の保存形式と互換性を保つ。宣言コメントは [Json-like-comment-outsの日本語仕様](https://github.com/tomiya7688/Json-like-comment-outs/blob/main/docs/jp/SPECIFICATION.md) に従い必須とする。関数・メソッドの「責務・処理・引数・戻り値」、型・クラスの「責務・フィールド」を宣言直前に書き、属性・デコレータの前にも置ける。公開APIだけでなく内部関数とテストも対象とし、空の雛形ではなく実装に合った説明を書く。実装内部の理由や注意点は通常のコメントで残す。
5. 作業単位に対応する自動評価を実行する。GUIは明示的に必要な場合以外は起動しない。`python scripts/check_declaration_comments.py` と `python scripts/check_declaration_comments.py --changed-base origin/main` で宣言コメントを検査する。後者は指定リビジョンからHEADまでの変更ファイル全体を対象とするため、コミット前は対象パスを明示して検査し、コミット後に変更範囲も検査する。変更した既存ファイルに古い未対応宣言があっても除外しない。構造の自動検査に加え、引数・戻り値・フィールドと説明が一致するかレビューし、不足した変更は差し戻す。
6. 評価結果と差分を確認する。失敗や未確認の項目を成功として扱わない。
7. 作業対象のファイルだけをコミットする。
8. main へ反映し、GitHubへ push する。push 後に作業ツリーとリモート反映を確認する。
9. 完了した開発予定の項目を削除または更新し、次の作業単位を明確にする。
