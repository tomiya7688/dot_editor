# 実装担当：1回の作業

<!-- workflow-role: implementer -->

対象は機能追加・修正・Issue対応を行う担当者です。目的は、小さい変更を自分でレビューし、問題を修正してmainへ反映することです。利用者の直接操作はありません。[担当の選択と共通開始確認](ワークフロー.md) を終えてから進めてください。

## 手順

1. 優先度・依存・既存の担当を確認し、今回完了するIssueまたは依頼の1単位を選んでください。既存PRの継続では差分と指摘を再確認してください。
2. 最新mainを基点に作業し、担当ブランチ・比較元SHA・所有するファイル・検証方法を記録してください。他の担当者の作業を上書きせず、無関係な変更を含めないでください。
3. [R01〜R20](../../コーディング規約.md) に従って実装・テスト・説明を変更してください。宣言コメントは [Json-like-comment-outs日本語正本](https://github.com/tomiya7688/Json-like-comment-outs/blob/main/docs/jp/SPECIFICATION.md) に従ってください。関数・メソッドの「責務・処理・引数・戻り値」と型の「責務・フィールド」は、内部宣言・テストでも必須です。処理の理由は通常コメントで説明してください。
4. 変更パスを明示して宣言コメント監査を行い、影響に応じた単体・回帰・互換・E2E・ビルドを実行してください。命名、責務、コメントの意味、境界値、失敗時の状態保護、効率、安全性、日本語を自分でレビューしてください。自動チェックだけでレビューを代用しないでください。
5. 問題があれば修正し、必要な回帰テストを追加して再検証してください。差分に関係する未解決指摘や、必要な未検証項目を残したままマージ可にしないでください。
6. 対象ファイルだけをコミットし、PRを作成または更新してください。コミット後も既定対象と比較元SHAからの差分のコメント監査を行ってください。PRへレビューしたHEAD、自己レビュー結果、具体的なテスト結果、未確認範囲を記録してください。
7. GitHubでHEADの一致、最新mainとの競合と影響、必要なpush／pull_requestのCI、指摘の対応、保護設定を確認してください。必要な個別ジョブまで確認し、失敗・実行中・必要な検証のスキップを成功扱いしないでください。main更新で影響が変わった場合は取り込み・再レビュー・再検証してください。
8. 問題がなく必要な検証・CIが成功したら、実装担当が通常のPRマージ操作でマージしてください。全体レビュアーの巡回や承認は待ちません。mainへの直接push、管理者権限でのゲート迂回、保護設定の無断変更は禁止です。
9. リモートを再取得し、マージ済み状態・mainのSHA・main側CI・作業ツリーを確認してください。失敗があれば影響を調べ、必要な修正を別の小さいPRで行ってください。他の作業を消してはいけません。
10. 開発予定と引き継ぎを更新し、自己レビュー・検証・マージ・main側CIの結果と次の1単位を報告してください。Issueは完了条件をすべて満たしたときだけ閉じてください。

## コメント監査の実行例

リポジトリルートで変更前に比較元を記録し、パスは今回の変更ファイルへ置き換えてください。

```powershell
$reviewBaseRevision = git rev-parse origin/main
.venv/Scripts/python.exe scripts/check_declaration_comments.py rust/crates/hyper-dot-core/src/field_bounds.rs
```

コミット後は同じ比較元を使ってください。

```powershell
.venv/Scripts/python.exe scripts/check_declaration_comments.py
.venv/Scripts/python.exe scripts/check_declaration_comments.py --changed-base $reviewBaseRevision
```

## 自己レビューと終了記録

```text
担当: implementer
対象Issue・PR / 比較元SHA / レビューしたHEAD:
自己レビュー: 問題なし / 修正した問題と再検証 / 保留理由
R01〜R20・既存指摘への対応:
テスト・CI: コマンド、結果、イベント、対象SHA
未確認・対象外:
マージ結果・mainのSHA・main側CI:
次の担当・最初の作業:
```

必要な確認ができない場合は理由と再開条件を記録してください。単に「独立レビュー待ち」として停止しないでください。自己レビューはGitHub上の他者承認とは異なります。
