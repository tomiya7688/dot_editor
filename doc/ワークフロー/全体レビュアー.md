# 全体レビュアー：1回の作業

<!-- workflow-role: repository-reviewer -->

対象はリポジトリ全体のレビューを明示的に依頼された担当者です。「単独レビュアー」もこの役割を指します。目的は、実装担当が着手できる根拠のある改善Issueを作ることです。PRの承認係ではありません。利用者の直接操作はありません。[担当の選択と共通開始確認](ワークフロー.md) を終えてから進めてください。

## 手順

1. リモートを更新して調査対象SHAを固定してください。前回の確認・未確認範囲を読み、今回はどの未確認領域や横断的な契約を調べるか決めてください。全体を対象にしますが、1回で全ファイルを確認済みにする必要はありません。
2. [R01〜R20](../../コーディング規約.md)、仕様、実装、テスト、CI、既存Issue・PRを照合してください。呼び出し元、保存互換、境界値、責務、効率、安全性、文書の使いやすさまで、必要に応じて調べてください。
3. 読み取り・非破壊の検証で再現条件と影響を確認してください。GUI・E2E・配布物・静的検査の証拠を区別し、未検証の推測は仮説と書いてください。利用者のファイルや他担当の作業を変更しないでください。
4. 重複するIssueを検索してください。既存Issueがあれば新しい根拠を追記し、重複起票しないでください。
5. 問題または改善案を、実装と検証が独立して完了できる単位のIssueにしてください。背景・目的・対象SHAと場所・再現または根拠・影響・優先度と理由・依存・提案手段・受け入れ条件・検証方法を記述してください。バグと任意の改善提案を区別してください。
6. 調査範囲、起票・追記したIssue、問題が見つからなかった範囲、未確認事項、次の調査範囲を報告してください。Issueを作ったことを修正完了とは表現しないでください。

## 役割の境界

- この担当では製品コードの修正・PRのマージ・他担当への作業割当を行いません。修正も明示的に依頼された場合は、別単位で実装担当へ切り替えてください。
- 全PRへの承認や、実装担当を自分の巡回待ちにすることは仕事に含みません。実装担当は自分の差分をレビューしてマージします。
- 対象PRに直接影響する重大な問題を見つけたら、PRとIssueへ根拠を関連付けて知らせてください。無関係な改善Issueまで一律にマージ条件へ追加しないでください。

## Issueと終了記録

```text
担当: repository-reviewer
調査対象SHA・今回の範囲:
種別: バグ / 改善提案 / 未検証の仮説
背景・目的:
対象ファイル・規則ID・根拠・再現:
影響・優先度と理由・依存:
提案手段・独立した実装範囲:
受け入れ条件・検証方法:
既存Issue・PRとの関係:
起票・追記したIssue:
未確認事項・次の調査範囲:
```

具体的な問題や改善案がなければ、無理にIssueを作らず確認範囲と限界を記録してください。
