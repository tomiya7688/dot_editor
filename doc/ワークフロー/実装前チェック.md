# 手戻りを防ぐチェック表（着手前・実装中・PR前・PR後）

## 背景と目的

実装そのものより、規則や環境の違いに気づかず、CIの失敗やレビューの差し戻しでやり直す時間が長くなりがちです。このページは、実際に起きた手戻りを、先に確認できる形で並べたものです。利用者の直接操作はありません。実装担当（`implementer`）が、各段階で上から順に確認します。**根拠のない「通るはず」は書かず、コマンドで確かめます。**

## 1. 着手前

| 確認 | 手戻りの原因 | 確認の方法 |
| --- | --- | --- |
| 設計書がある | 仕様の食い違いで実装をやり直す | [設計書の一覧](../../docs/design/README.md)。なければ[書き方](設計書.md)に従って先に書く |
| 依存するIssueと、他のPR | 先行の変更と衝突する | `gh issue view <番号>`、`gh pr list`、`git fetch origin` |
| 作業場所 | Cドライブの空きを使い切る。パスが長すぎてWindowsで削除できない | `git worktree list`。worktreeは`E:/projects/worktrees/<題材>/<repo>`に作る。パスは短く |
| 他の人の未コミット変更 | 他者の作業を上書きする | `git status`。自分の変更でないものは触らず、worktreeを分ける |
| GUIを起動しない | 評価でウィンドウが開く | 明示的に必要な検証以外では起動しない |
| レビュー手順の確認 | 規定の外部レビューを抜かす | 作業の開始時と完了前に、レビュー運用の手順書を開く（運用規則） |

## 2. 実装中

| 確認 | 手戻りの原因 | 確認の方法 |
| --- | --- | --- |
| 宣言コメント | 関数・内部関数・テスト・`__init__`・入れ子の関数にも必要。形式が違うとCIで失敗 | `python scripts/check_declaration_comments.py <ファイル>`（**フォルダは渡せない**。ファイルを並べる） |
| Pythonの整形 | 固定版のRuff 0.17.2で整形していないとCIで失敗 | `python scripts/format_python.py <変更したPython>`、その後`--check` |
| Rustの整形 | 複数のcrateでは`--all`が要る。無いと`Failed to find targets` | `cargo fmt --all --manifest-path rust/Cargo.toml -- --check` |
| clippy | 警告があるとCIが止まる。型が複雑という指摘は型別名で直す | `cargo clippy --manifest-path rust/Cargo.toml --workspace --all-targets --all-features -- -D warnings` |
| 実行ファイルのパス | 子プロセスの作業フォルダが違うと、相対パスでLinuxだけ失敗する | テストや検査で起動するパスは絶対パスにする |
| OSの違い | Windowsだけ・Linuxだけで動く | 拡張子`.exe`、パス区切り、改行、実行権限、環境変数を意識する。CIの`ubuntu`が最終確認 |
| 成果物のアップロード | `actions/upload-artifact`を使うとセキュリティのテストが失敗する（#55が完了するまで禁止） | ジョブの要約（`$GITHUB_STEP_SUMMARY`）に書く |
| READMEの内容 | 担当者向けの語（`AGENTS.md`、`Claude Code`、`Codex`、`docs/agents/`、ワークフロー等）が混ざると検査が失敗 | READMEには利用者向けの説明だけを書く |
| 未実装の機能の書き方 | 現行の契約に未実装のコマンドを書くと利用者が誤解する | 「次期」「未実装」の節に分ける |
| ジョブ名・チェック名 | 名前を変えると保護設定の必須チェックが見つからなくなる | 変更は保護設定の更新と同じPRで扱う（[手順書](../../docs/design/main-protection-runbook.md)） |

## 3. PRを作る前

| 確認 | 手戻りの原因 | 確認の方法 |
| --- | --- | --- |
| 関連テスト | 一部だけ通して出す | 変更に関係するテストを全て実行し、結果を控える。実行していないものは「未確認」と書く |
| 全体の検査 | 変更したファイル以外の検査（既定対象）が失敗する | `python scripts/check_declaration_comments.py`（既定）、`--changed-base origin/main` |
| 追加の対象 | 設計書を足したのに一覧へ載せていない | `docs/design/README.md`に1行足す（検査あり） |
| PR本文 | 5つの節が無い、短すぎる、Issue番号が無い、Validationに実行内容が無い、**改行がCRLF** | `## Issue`/`## Summary`/`## Validation`/`## Risks`/`## Handoff`を各1つ。Issue番号`#N`と、実行したコマンドを書く。ファイルは**LF**で保存して`gh pr create --body-file` |
| コミットの注記 | 規定の共著表記が無い | 規定の行を末尾に付ける |
| 外部レビュー | 手順の省略に根拠が無い | 規定の6者に依頼。省略は、今回のエラーやタイムアウトの証拠を残す。PR後はCodeRabbit |

## 4. PRを作った後

| 確認 | 手戻りの原因 | 確認の方法 |
| --- | --- | --- |
| CIの全ジョブ | 一部が実行中・失敗・スキップなのに成功と報告する | `gh pr checks <番号>`。失敗は原因のログを読んで直す。実行中を成功と書かない |
| HEADの一致 | マージ時に別のコミットが入る | `gh pr merge <番号> --merge --match-head-commit <SHA>` |
| mainの更新 | 取り込まずに競合する | `git fetch origin`、必要なら取り込んで再検証 |
| レビューの指摘 | 古いHEADの指摘を無視する | 具体的な指摘は、新しいHEADの該当箇所と照合する |
| 後片付け | 残ったworktreeが容量を使う | 未コミットの変更がないことを確かめてから`git worktree remove` |

## 5. 迷ったとき

- 契約や設計と食い違う実装を見つけたら、実装を変える前に設計書を直す（[設計書の書き方](設計書.md)）。
- 費用・契約・保護設定・過去の成果物の削除は、担当者が決めず、所有者に報告する。
- 失敗・未確認・実行中は、成功扱いにしない（[実装担当](実装担当.md)の終了記録）。
